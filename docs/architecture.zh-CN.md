# 架构：设备的分布式应用底层基础设施

[English](architecture.md) | 中文

hyperdht-esp32 让一块 ESP32-C3 模组成为 Holepunch 网络中的一个节点。集成了这块模组的设备，不需要自建后台，就能获得分布式应用最底层的四项能力：

- **身份**：由设备自己生成、自己持有。
- **地址**：由身份派生，可以穿透 NAT，从任何地方被找到。
- **端到端加密通道**：任何知道设备公钥的一方都能和它建立加密通道，走互联网或 BLE 均可。
- **记录**：设备可以用自己的密钥发布签名记录（例如 DID 文档），任何人都能自行验证。

本文说明这些部分如何组合、各自保证什么，以及产品如何基于它们构建。字节级协议见 [`protocol.md`](protocol.md)，API 见 [`components/hdht/README.md`](../components/hdht/README.md)。

## 设计原则

1. **密钥就是身份，身份就是地址。** 别人通过设备的 Ed25519 公钥找到它，不需要 IP 地址、域名或云账号，也不需要先去任何地方注册。
2. **数据路径上没有自建服务器。** 设备通过公共 HyperDHT 找到对端，然后直接通信。DHT 节点只帮双方找到彼此、转发握手，看不到通信内容。
3. **端到端加密并认证。** 每条通道都先完成 Noise 握手，证明双方各自持有声称的公钥。设备确切知道对面是哪把密钥，对端也一样。
4. **数据自证。** 用某把密钥发布的记录由这把密钥签名。读取方自己验证，不需要信任存储它的节点或转交它的一方。
5. **与参考实现线上兼容。** C 实现逐字节遵循 hyperdht 6.x 协议，对端可以是未经修改的 Node.js `hyperdht` 应用。
6. **设备只做轻客户端。** 设备以临时、防火墙后的节点身份加入 DHT：使用网络，但不为别人做路由，从而压低内存、功耗和流量。
7. **在线离线同一身份。** 没有互联网时，同一把密钥可以通过 BLE 建立同样的加密通道。

## 分层结构

```
 ┌──────────────────────────────────────────────────────────────────────────────────┐
 │ 产品应用                                                                            │
 │   遥测、控制、配置、支付（例如 BoAT MER 0xEE00）……                                  │
 ├──────────────────────────────────────────────────────────────────────────────────┤
 │ 应用协议（由产品定义）：在加密流之上的消息格式                                      │
 ├────────────────────────────┬───────────────────────────┬─────────────────────────┤
 │ 身份                        │ 可达性与通道               │ 记录                     │
 │  NVS 中的 Ed25519 密钥对    │  hdht_listen（服务端）     │  hdht_mutable_put / get  │
 │  DID = did:mw:<公钥>        │  hdht_connect（客户端）    │  例如 DID 记录           │
 │                             │  hdht_ble（本地）          │                          │
 ├────────────────────────────┴───────────────────────────┴─────────────────────────┤
 │ hdht 核心（components/hdht）                                                       │
 │  dht-rpc 查询 · announce · 中继 Noise IK/XX 握手 · 打洞 · SecretStream             │
 ├──────────────────────────────────────────────┬───────────────────────────────────┤
 │ libudx：带 BBR 的可靠 UDP 流                  │ NimBLE GATT（components/hdht_ble） │
 │ uv_esp：基于 lwIP 的 libuv 子集               │                                    │
 ├──────────────────────────────────────────────┴───────────────────────────────────┤
 │ ESP-IDF · FreeRTOS · WiFi · BLE · libsodium · NVS                                  │
 └──────────────────────────────────────────────────────────────────────────────────┘
```

从 `uv_esp` 往上的所有部分都运行在**同一个事件循环任务**里。其他任务通过 `uv_async_send` 把工作交给它。

与 Holepunch 技术栈的对应关系：

| 层 | Holepunch（JS） | 模组上 |
|---|---|---|
| 应用、存储 | Pear、Hypercore、Autobase | 不在设备上实现；对端可以运行 |
| 按 topic 发现 | Hyperswarm | `hdht_lookup` / `hdht_announce`：设备能找到在某个 topic 下宣告的对端，也能在 topic 下宣告自己 |
| 点对点连接 | hyperdht | `components/hdht`（C） |
| 记录 | hyperdht `mutablePut` / `mutableGet` | `hdht_mutable_put` / `hdht_mutable_get` |
| DHT RPC | dht-rpc | `components/hdht`（C） |
| 加密 | Noise、SecretStream | `components/hdht`，基于 libsodium |
| 传输 | libudx、libuv | libudx（内置）、`uv_esp` |

## 基础能力

产品能拿到的构件如下，每一项都可以单独使用。

| 能力 | API | 作用 | 状态 |
|---|---|---|---|
| 密钥对 | `hdht_keypair(pk, sk, seed)` | 由 NVS 里的 32 字节种子派生 Ed25519 身份 | 已完成 |
| 监听 | `hdht_listen(密钥对, ...)` | 设备可以按公钥从任何地方被连接；约每 5 分钟重新 announce，并保持中继路径存活 | 已完成 |
| 连接 | `hdht_connect(公钥, ...)` | 按公钥连接任意 HyperDHT 服务端，得到加密流：直连、局域网或打洞 | 已完成 |
| 流 | `hdht_stream_write / end / destroy` | 有序、可靠、加密的消息，与 `@hyperswarm/secret-stream` 线上兼容 | 已完成 |
| 记录 | `hdht_mutable_put / get` | 最大 1000 字节的签名值，存在离该公钥最近的约 20 个 DHT 节点上，任何人都能读取并验证 | 已完成 |
| 本地通道 | `components/hdht_ble`、`secret_stream.h` | 同样的 SecretStream 跑在 BLE GATT（或任意字节流）上，使用同一个身份 | 已完成 |
| topic 查找 | `hdht_lookup` | 找到在某个 topic 下宣告的对端（如 Hyperswarm 服务端）；回复只是线索，连接时才认证 | 已完成 |
| topic 宣告 | `hdht_announce` / `hdht_unannounce` | 让别人按主题而不是按公钥找到自己 | 已完成 |
| 中继 | `hdht_set_relay`；对端的 `relayThrough` | 无法打洞时（如设备在随机型 NAT 后面）经 blind-relay 节点连接 | 已完成；保持走中继，不会升级为直连 |

## 身份

一把 Ed25519 密钥对就是设备的身份：

- **在设备上生成。** 首次开机用随机种子生成，存进 NVS（量产时请启用 NVS 加密），永不离开设备。
- **公钥就是地址。** 对端在 DHT 上查找 `BLAKE2b(公钥)`，`hdht_listen` 宣告的正是这个值。
- **公钥就是 DID。** 和 BoAT MER 一样，`did:mw:<公钥十六进制>` 指向同一把密钥，所以可以直接按 DID 拨号。从 DID 到公钥不需要解析服务，因为 DID 本身就是公钥。
- **每次连接都会认证。** Noise 握手证明服务端持有被拨号的那把密钥，同时把客户端公钥交给服务端（`stream->remote_public_key`）。设置 `hdht_opts_t.seed` 后，设备主动发起的连接也使用自己的身份。

**其他密钥通过记录挂在这把密钥下面。** 产品往往还需要别的密钥，例如用于支付的 secp256k1 钱包。做法是：设备用身份密钥签发一条记录，写明这些密钥；每把被写进去的密钥再反过来签名 DID。下文的 [DID 记录](#did-记录) 就是这样绑定钱包的。

**密钥复用。** 同一把身份密钥要做三件事：Noise 密钥交换、DHT announce 签名、记录签名。三者都有域分离：每次签名的内容都是一个 32 字节的命名空间加一个哈希，所以为某个用途做的签名无法挪作他用。如果产品要求严格分离，可以从同一个种子派生多把密钥，再用记录把它们关联起来。

**密钥轮换**目前不内置：换新密钥就等于换了地址和 DID。可以让旧密钥发布一条指向新密钥的记录；更完整的方案（controller 密钥）列在[缺口](#缺口与路线图)里。

### DID 记录

[`examples/boat_mer`](../examples/boat_mer) 定义了一份不需要注册中心的精简 DID 文档：

```json
{"v":1,"did":"did:mw:<ed25519 公钥>","eth":"0x<钱包地址>","eth_sig":"0x<对 did 的 EIP-191 签名>"}
```

- **DID 认领钱包。** 记录用 `hdht_mutable_put` 存在 DID 密钥名下：只有 DID 密钥签过名的记录，DHT 节点才会接受，读取方也才会返回。
- **钱包认领 DID。** `eth_sig` 是钱包对 DID 的签名，所以没人能把别人的钱包说成是自己的。
- **只需 DID 就能验证。** 任何知道 DID 的人都能查到记录并检查两个签名，不需要其他任何信息。
- **需要定期重发布。** 节点最多保存记录 48 小时，设备每 30 分钟重发一次。记录带签名，所以任何人都可以代为重发，但谁也改不了内容。
- **seq 规则。** seq 高的记录替换 seq 低的。内容固定的记录（MER 使用 RFC 6979 确定性签名）每次开机都可以按原 seq 重发。

同样的模式也可以承载其他声明：固件版本、能力、服务入口、制造商凭证。

## 典型流程

### 对端连接设备

```
 设备                             HyperDHT 节点                          对端（Node / Pear / 手机）
   │ ANNOUNCE BLAKE2b(pk)  ─────────▶ │                                       │
   │                                  │ ◀──────────── FIND_PEER BLAKE2b(pk)    │
   │ ◀────── 中继的 Noise IK 握手（双方公钥得到证明）────────────────────────▶ │
   │ ◀────── 中继的打洞消息：地址、NAT 类型 ──────────────────────────────────▶ │
   │ ◀════════════ 直连 UDP（libudx）+ SecretStream，端到端 ═════════════════▶ │
```

1. `hdht_listen` 向最近的 3 个节点宣告设备，并每 3 秒 ping 一次，让它们能为设备转发。
2. 对端查找公钥，节点转发 Noise IK 握手。握手完成后，双方都已证明各自的公钥。
3. 双方在加密的中继消息里交换各自的地址和 NAT 类型，然后互相打 UDP 洞。如果在同一局域网，就直接连接。
4. 数据流在双方之间直接传输，DHT 节点不再参与。

### 设备连接对端

流程相同，方向相反：`hdht_connect(公钥)` 查找对端，作为发起方完成握手并打洞。设备调用服务、连接其他设备或连接卖方，都走这条路径。

### 发布与解析记录

```
 设备：hdht_mutable_put(pk, sk, seq, value)    任意读取方：mutableGet(pk) / hdht_mutable_get(pk)
   │ 向 BLAKE2b(pk) 发起 MUTABLE_GET 查询，收集 token               │
   │ 向约 20 个节点发送 MUTABLE_PUT {pk, seq, value, 签名} ──▶ 节点 ◀── MUTABLE_GET ── │
   │                                                                │ 验证签名，取最高 seq
```

在公网上，一次查找就是一次 DHT 查询，通常 2–7 秒。需要频繁查询的调用方应当缓存结果，并在后台刷新。

### 本地离线

手机或电脑在设备旁边通过 BLE 连接，对同一把密钥跑同样的 SecretStream 握手。设备在广播里带上自己 DHT target 的前几个字节，客户端连接前就能确认找对了设备。产品的应用协议在两种传输上可以完全相同；在参考集成里，MER 的 0xEE00 协议就是这样。

## 信任模型

各方可以依赖什么，以及依据是什么：

| 声明 | 依据 | 信任对象 |
|---|---|---|
| “我在和密钥 K 的持有者通信” | Noise IK/XX 握手 | 只有密钥 |
| “路径上没人能读取或篡改数据流” | 由握手派生密钥的 SecretStream（XChaCha20-Poly1305） | 只有密钥 |
| “这条记录是 K 发布的” | 读取方验证 Ed25519 签名 | 只有密钥 |
| “这是 K 的最新记录” | 所问节点中 seq 最高的那条 | DHT 如实返回；节点可以扣下记录，但无法伪造 |
| “K 的钱包是 W” | K 签名的 DID 记录，加上 W 对 K 的 DID 的签名 | 只有这两把密钥 |
| “K 是制造商 M 的正品设备” | 暂未实现：记录里携带由 M 签发的凭证 | M 的公钥 |
| “K 可以连上” | DHT 上的 announce | DHT 节点大体如实转发握手；节点无法冒充 K |

DHT 能对你做的坏事：拒绝存储或返回记录，或者不转发握手。这些都属于拒绝服务，它无法冒充密钥、读取数据流或伪造记录。

DHT 不负责准入。任何密钥都能加入网络、宣告自己、发布记录。“这是不是我们家的真设备”要靠你信任的发行方签发的凭证来回答，凭证可以放在记录里。

## 各部分在哪里运行

| 组件 | 谁运行 | 是否必需 |
|---|---|---|
| 设备固件 | 你，在模组上 | 必需 |
| HyperDHT 引导与路由节点 | 公共节点（引导节点由 Holepunch 运营），任何人都可以加节点 | 必需，但不用你来运营。私有网络可以用 `hyperdht` 自建，并通过 `hdht_opts_t.bootstrap` 让设备指向它 |
| 与设备通信的对端 | 你的应用：Node.js、Pear、桌面端、手机 | 你的产品 |
| 记录重发布者和索引 | 可选：任何持有签名记录的进程 | 只有两种情况需要：设备离线时让记录保持存活；需要列出设备时（DHT 只能按公钥查，不能搜索） |
| 结算、发行方、吊销列表 | 可选：区块链或只追加日志 | 只在需要支付或准入时 |

数据路径上没有中心服务器。可选服务放在旁边，在内容上不需要被信任：重发布者改不了记录；索引只能指向记录，读取方会自行验证。

## 基于它构建产品

如果产品自己的主控 MCU 跑应用，可以保持原有固件不变，通过串口把 C3 当作模组来驱动：见 [`examples/uart_module`](../examples/uart_module)，命令说明在 [`module-uart.md`](module-uart.md)。

[`examples/app_template`](../examples/app_template) 把下面这些步骤合在了一起：身份、记录、认领、授权、撤销，以及任何对端都能保存的签名读数。复制它，再替换 `app.c` 即可。

**1. 硬件预算。** ESP32-C3，4 MB flash。WiFi 加 hdht 的固件约 1.06 MB，带 BLE 再加 0.22 MB。规划一个 20 KB 栈的任务，每条活跃连接约 25 KB 堆。

**2. 首次开机建立身份。** 生成种子，存入加密 NVS，派生密钥对。如果用户需要配对，出厂时打印或贴上公钥（或 DID），并发布一条描述设备的记录。

**3. 选择角色。**
- *服务端*（始终可达）：使用 `hdht_listen`。WiFi 要一直开着，每 3 秒 ping 一次中继节点，适合市电供电的设备。
- *客户端*（主动外连）：使用 `hdht_connect`。会话之间可以休眠，适合电池设备。
- *本地*：使用 `hdht_ble`，用于初始设置、离线控制或手机配对。

**4. 定义应用协议。** 把协议设计成数据流上的消息，并且不绑定传输方式，这样同一套代码既能跑在 HyperDHT 上，也能跑在 BLE 上。参考集成使用 `op | id | value` 帧，每条消息一帧。

**5. 决定谁可以连接。** 数据流会告诉你对端的公钥。执行命令前，先用白名单、记录或凭证核对它；DHT 不会替你做这一步。

**6. 保持事件循环响应。** hdht 的全部工作都跑在一个任务里。耗时操作（例如 0.5 秒的 secp256k1 签名）运行时会阻塞网络。如果这类操作很频繁，就放到另一个任务里执行，结果用 `uv_async_send` 交回循环。

**7. 配置。** `CONFIG_FREERTOS_HZ=1000`、`CONFIG_LWIP_UDP_RECVMBOX_SIZE=32`，以及足够大的应用分区。详见 [`components/hdht/README.md`](../components/hdht/README.md#esp-idf-requirements)。

## 参考集成：BoAT MER

[`examples/boat_mer`](../examples/boat_mer) 把模组和 [BoAT MER](https://github.com/TLAY-IO/boat-mer) 结合在一起。MER 是一个 C 运行时，提供设备身份、签名数据和 EIP-3009 小额支付。这个例子用到了全部基础能力：

| 能力 | 用法 |
|---|---|
| 身份 | MER 的 Ed25519 密钥直接作为 HyperDHT 密钥，设备的 DID 就是它的网络地址 |
| 监听 | 任何人都能按 DID 拨号设备，拿到一份由 MER 证明的读数 |
| 连接 | 设备作为买方，按公钥连接远端卖方 |
| 流 | MER 原本跑在 BLE 上的支付协议（0xEE00）原样跑在 HyperDHT 数据流上 |
| 记录 | 买卖双方各自发布绑定钱包的 DID 记录。买方只向卖方记录里的钱包付款，卖方只接受由买方记录里的钱包签名的付款 |
| 锚定 | 签名读数同时提交给多个开放锚定节点（通过 topic 查找发现），而不是一台 HashAnchor 服务器（[节点运营指南](anchor-node.md)）。每个节点自行打包，在无权限合约上锚定，并保留一份可复制的日志；回执与 HashAnchor 的验证函数兼容 |

在公共 HyperDHT 上的实测结果：
- 支付授权共 53 + 24 笔通过验证，没有被拒的。
- 账单填错收款钱包的卖方，4 次全部被拒。
- DID 记录存进了 20/20 个节点。

详见它的 [README](../examples/boat_mer/README.md)。

## 资源占用

测试芯片为 ESP32-C3（160 MHz），数据来自 [`examples/hyperdht_demo`](../examples/hyperdht_demo/README.md) 和 [`examples/boat_mer`](../examples/boat_mer/README.md)：

| 项目 | 数值 |

| 每条连接的堆峰值 | 约 25 KB |
| 剩余堆（WiFi + DHT，连接进行中） | 约 165 KB |
| 剩余堆（WiFi + DHT + BLE，全部忙碌） | 约 50 KB |

| 公网 DHT 引导 | 约 3 秒 |
| 局域网内按公钥连接 | 约 0.5 秒 |
| 跨家用路由器和运营商 NAT 连接 | 9–32 秒 |

| Noise 握手 | 每侧约 0.2 秒（软件加密） |
| 局域网吞吐 | 313–365 KiB/s，受 CPU 限制 |

## 缺口与路线图

目前已知的限制，大致按对产品的影响排序：

| 缺口 | 影响 | 方向 |
|---|---|---|
| 需要有人运行中继节点 | 随机型 NAT 后面的设备需要一个有公网地址的 blind-relay 节点，目前还没有公共服务 | 运行中继节点，并让设备按 topic 找到它们 |
| 中继连接不会升级 | 即使后来能直连，流量仍走中继 | 像 hyperdht 那样，打洞成功后升级为直连 |
| 没有准入 | 任何密钥都能自称是设备 | 在 DID 记录里放制造商凭证，吊销列表放在区块链或只追加日志上 |
| 不支持密钥轮换 | 换密钥就换了 DID | 签名的“迁移到”记录，或在 DID 记录里加入 controller 密钥 |
| 不能列出设备 | DHT 只能按公钥查 | 在记录之上建索引，例如由发行方写入的 Hypercore/Hyperbee 日志 |
| 未与 Pear/Hyperswarm 应用实测 | 预计可以通过 `swarm.joinPeer(publicKey)` 连接，它走的是同一条连接路径 | 测试并写入文档 |
| 服务端功耗 | 每 3 秒的中继 ping 让 WiFi 一直开着 | 电池设备用客户端角色，或拉长间隔、接受更慢的故障切换 |
| 只支持 ESP32-C3 | 其他芯片未测试 | 移植到其他 ESP32 型号 |
| 缺少 Protomux、IPv6、immutable 记录 | 协议功能少于 hyperdht | 按产品需要逐步补齐 |
